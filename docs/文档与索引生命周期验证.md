# 文档身份、版本发布与索引生命周期

版本：0.8.0；日期：2026-11-20。对应建设计划第 5 项。

## 身份与版本

| 概念 | 规则 |
| --- | --- |
| 品牌 | 所有身份、版本、操作与查询按品牌隔离 |
| `logical_id` | 稳定的逻辑文档身份，如厂商资料编号；去首尾空白、区分大小写，不依据文件名或版本标签猜测 |
| `doc_id` | 内容版本 ID，保留原有生成方式；一旦登记，不能换绑来源哈希或逻辑身份 |
| `source_hash` | 完整来源哈希，用于检查版本绑定及原件；解析／规则再次处理可产生新运行，不改来源绑定 |
| `document_version` | 人工版本标签，仅展示和筛选；不按 `v2`、日期等标签自动比较先后 |
| 生命周期修订号 | 同一逻辑文档下的操作并发检查值，与元数据修订号分开 |

未填写 `logical_id` 的新文件使用自身 `doc_id`，旧库也按此建立独立组。相同文件名不会自动替换。新文件明确填写已有逻辑身份，表示提交该资料的修订：通过后替换活动版本；待复核／失败不会挤掉其他已通过版本。同一批次每个身份只能提交一个内容版本。

同组意味着替换，不能表达多个车型／市场的资料并行有效。需要并存的手册应使用不同身份；品牌相同也不会推断它们属于同一资料。

上传表格新增 `logical_id` 列，支持逐文件填写；CLI 的 `--logical-id` 只用于单文件。已登记版本不允许用重新导入换绑身份。已有独立默认身份的两个版本，可通过显式替换合并；有其他显式身份或多个版本的目标组不被隐式合并。合并后的默认身份不是新的独立组，后续应使用 `versions` 返回的注册身份。

```bash
uv run autorepair process examples/lifecycle/first.html --brand aurora \
  --logical-id demo-manual --output work/lifecycle-example
uv run autorepair process examples/lifecycle/second.html --brand aurora \
  --logical-id demo-manual --output work/lifecycle-example
uv run autorepair versions --brand aurora --database work/lifecycle-example/knowledge.sqlite
```

## 审核状态与发布状态分开

质量状态仍为 `passed/review/failed`；版本发布状态为：

| 状态 | 是否正式召回 | 含义 |
| --- | --- | --- |
| `active` | 是，且仍需通过门禁 | 同一逻辑身份最多一个活动版本 |
| `staged` | 否 | 待审核／失败候选，或被组级撤下保护的新版本 |
| `superseded` | 否 | 已被替换的历史版本，保留审计 |
| `withdrawn` | 否 | 人工撤下，重新加工不会自动复活 |

- 活动版本本身重新处理为待复核／失败时，会停止召回；不会悄悄回退到较早的通过版本。
- 撤下活动版本会暂停该逻辑文档组，新导入的通过版本也暂存，直到显式恢复选中的通过版本。
- 恢复／回退要求该版本**最近保存的处理结果仍通过且无未解决问题**，不能选一个更早的通过运行绕过后来的失败结果。
- 恢复较早通过版本，会将当前活动版本转为已替换；不会解除其他版本的审核问题。恢复不自动用当前磁盘 YAML 重跑规则，规则更新后应先重加工。
- 修正非活动版本的元数据不会重新发布。活动文档、持久化切块、版本指针及审计在同一事务中更新，出错全部回滚。

```bash
# DOC_ID、修订号和目标运行 ID 均从 versions 获取，不原样使用占位值
uv run autorepair withdraw --brand aurora --doc-id DOC_ID --expected-revision 1 \
  --actor '本地维护人' --reason '暂时撤下核对'
uv run autorepair restore --brand aurora --doc-id DOC_ID --expected-revision 2 \
  --actor '本地维护人' --reason '恢复最近已通过版本'
uv run autorepair version-replace --brand aurora --doc-id CURRENT_DOC_ID \
  --replacement TARGET_DOC_ID --expected-revision 3 --expected-target-run TARGET_RUN_ID \
  --actor '本地维护人' --reason '已核对为同一资料的修订'
uv run autorepair lifecycle-history --brand aurora
```

以上未指定数据库时使用 `artifacts/knowledge.sqlite`。演示或其他库需增加 `--database PATH`。操作人是本地署名，不等同登录身份认证。

## 索引维护

当前维护的是 SQLite 中的发布文档和章节切块索引；BM25 每次从活动块构建内存排序，没有声称实现向量索引。

- 重复导入同一内容仍保留运行审计，但不增加内容版本或重复切块；内容、配置及索引指纹相同时跳过切块写入。
- 检查文档摘要、切块配置、块数及实际切块内容指纹，能发现“数量没变、内容已损坏”的情况。
- 修复以活动版本的已通过运行作为依据；正文缓存损坏或丢失时恢复该快照，不把损坏正文重新视为通过。
- 增量维护只修复差异，重建重新生成当前品牌的全部活动块；清理过期发布缓存和孤立索引，不复活撤下版本，不影响其他品牌。
- 启动默认自动校验／补建。CLI `index --mode check` 刻意关闭自动修复，以便先报告原有问题；维护操作带署名、原因和审计。
- 指纹用于一致性检查，不是对能够任意修改数据库全部表的攻击者提供防篡改认证。缺少可恢复审核正文时停止维护，不伪造通过记录。

```bash
uv run autorepair index --brand aurora --mode check
uv run autorepair index --brand aurora --mode incremental --actor '维护人' --reason '修复差异'
uv run autorepair index --brand aurora --mode rebuild --actor '维护人' --reason '重建活动资料索引'
```

## 本地原件保留与清理

已经留存的原件默认持续保留，不设自动过期天数。撤下、替换、索引重建和应用重启都不会自行清理原件。

显式清理流程：

1. 生成计划，列出当前品牌下已撤下／已替换版本的数据库原件副本、来源哈希、逻辑字节数及保护数量。
2. 活动版本、暂存候选及无法可靠绑定版本的旧原件默认保护。计划中的具体范围以令牌绑定，相关变更后须重新预览。
3. 按令牌执行，填写署名和原因；删除对应 `source_files` 行，保存清理记录。测试只清理隔离自制库，没有清理用户的实际原件库。
4. 已清理原件保留标记；重复导入不会自动补回。恢复文档后可检索保留的解析证据，但原页明确显示已清理，需要显式 `source-attach` 校验同哈希原件才能补挂。

```bash
# 默认只预览
uv run autorepair source-cleanup --brand aurora
# 使用上一步的实际 plan_token 执行
uv run autorepair source-cleanup --brand aurora --apply --plan-token PLAN_TOKEN \
  --actor '维护人' --reason '清理已退出发布的数据库原件副本'
```

**清理只针对本库原件副本。** 不删除最初的源文件、历史处理正文、图片附件、元数据／生命周期审计、旧导出和外部备份；不等同设备级安全擦除。计划字节数是逻辑删除量，不保证 SQLite 文件立即缩小。原件是否保留不改变审核状态，也不阻止通过文本版本恢复。

## 导出与历史审计

新增 `publication.json`，区分质量与发布状态。`knowledge.jsonl`、`knowledge-chunks.jsonl` 仅包含当前活动、且与本次运行一致的资料；规范 JSON 显式保存注册身份。`passed/` 表示通过质量检查，不等于当前仍活动。

历史导出不被反向重写，`--run` 查询及历史证据是当时的审计快照，不作为当前发布状态。旧库迁移保留已有当前通过项，不根据文件名、版本标签或时间猜测版本关系。
